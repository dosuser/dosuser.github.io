10분마다 다시 시작된 AI 에이전트: 4.38억 토큰이 기록된 자동화 사고

부팅과 함께 시작된 로컬 에이전트 게이트웨이가 Codex 작업을 10분마다 반복해 84개 루트 세션과 4.38억 토큰을 기록한 사건의 원인, 실제 산출물, 중단 과정과 재발 방지책을 정리한다.

게시 2026/08/23
By SHIN DAE YONG
23 분읽는 시간

백그라운드 AI 에이전트가 Mac 로그인과 함께 시작돼 10분마다 새 루트 세션을 만들었다. 일부 회차에서는 실행 가능한 작업을 고를 수 없었지만 예약 작업은 멈추지 않았다. 많은 회차에서 작성된 작업일지는 다음 회차의 입력으로 다시 들어갔다.

이틀 동안 예약 루트 세션 84개와 칸반 작업일지 72개가 확인됐다. 루트 세션 기록에는 입력과 출력 합계 437,993,236 tokens가 남았다. 조사 범위에서 확인된 commit, push, PR, 배포 기록은 0건이었다.

결론: 한 번의 잘못된 모델 응답이 아니라, 자동 시작·불완전한 작업 계약·자기 산출물 재입력·잘못된 활동 추적·중단 장치 부재가 결합한 자동화 제어 실패였다.

이 글은 2026년 8월 23일 로컬 실행 기록을 기준으로 쓴 사건 보고서다. 회사·사람·내부 프로젝트·이슈 번호·사내 URL·사용자 경로는 제거했다. 제품 단독 결함으로 단정할 증거도 없으므로, 특정 제품의 버그가 아니라 로컬 자동화 시스템의 복합 사고로 다룬다.

숫자를 읽기 전에 알아둘 점

437,993,236 tokens는 로컬 루트 세션에 기록된 입력·출력 누계다. 실제 청구 토큰이나 금액과 같다고 단정할 수 없다. 하위 에이전트 사용량은 이 합계에 포함되지 않았을 수 있다. 과금 단가와 캐시 적용 여부도 확인하지 않았으므로 비용을 달러나 원화로 환산하지 않았다.

OpenAI의 Codex 안내도 작업의 크기와 실행 시간이 사용량에 영향을 준다고 설명한다. 원문 표현은 “A long-running task can use substantially more than a short request.”다. (OpenAI Help Center)

사고 흐름: 부팅부터 재예약까지

Mac의 사용자 LaunchAgent가 로컬 에이전트 게이트웨이를 시작했고, 게이트웨이 안의 백로그 처리 작업이 Codex 프로세스를 10분마다 실행했다. Apple 문서도 사용자 로그인 시 “a per-user launchd is started”라고 설명하며, 사용자 Library/LaunchAgents의 설정을 읽는다고 명시한다. (Apple, Creating Launch Daemons and Agents)

부팅 자동 시작, 10분 주기 실행, 불가능한 작업 선별 계약, 자기 산출물의 재입력, 오류 후 무제한 재예약이 하나의 고리를 만들었다. 그림을 누르면 원본 크기로 확대된다.

직접 실행 체인은 다음과 같았다.

Mac 로그인 → 사용자 LaunchAgent → 로컬 에이전트 게이트웨이 → 10분 주기 백로그 처리 작업 → Codex 루트 세션

외부 사용자가 원격으로 실행했다는 증거는 없었다. 반대로 최초 예약 작업을 누가 어떤 명령으로 만들었는지는 생성자 기록이 남아 있지 않아 특정하지 못했다. 확인할 수 있었던 것은 현재 실행 주체와 반복 경로였다.

많은 회차에서 실제로 무엇을 했나

예약 작업의 요청은 “작업 보드에 등록된 일을 진행하고 항상 기록을 남긴다”는 형태였다. 에이전트는 안전 규칙을 지키려 했고, 작업일지가 남은 많은 회차에서는 다음 절차가 반복됐다.

  1. 전역 지침과 작업 규칙을 다시 읽었다.
  2. 같은 보드 캐시의 해시와 항목 수를 검사했다.
  3. 최근 작업일지 10~15개를 다시 대조했다.
  4. 저장소 잠금과 중복 작업을 검사했다.
  5. 실행 가능한 후보가 없으면 안전 보류했다.
  6. 그 결과를 새 작업일지로 작성했다.
  7. 새 작업일지가 다음 회차의 입력이 됐다.

사건 당시 감사 기록에는 다음 문장이 남아 있다.

“일지가 늘수록 대조 비용만 커진다.”

작업일지는 원래 감사와 인수인계를 위한 좋은 장치다. 문제는 자기 산출물을 반복해서 다음 프롬프트에 다시 넣은 것이다. 빈 회차도 새 문서를 만들고, 다음 회차는 더 많은 문서를 읽는다. 출력이 다음 입력을 키워 다시 출력을 만드는 되먹임이 형성됐다.

왜 실행 가능한 후보가 0건이었나

중간 감사 시점의 보드에는 담당 미완료 카드가 69개 있었다. 카드 수가 부족한 것이 아니었다. 자동 선별 규칙이 요구한 핵심 필드가 보드 스키마에 존재하지 않았다.

보드에 있던 정보 자동 선별이 추가로 요구한 정보
상태, 키, 담당자, 저장소, 제목, 갱신 시각 입력 자료
URL, 보드 열 예상 출력
  완료 조건
  검증 절차

감사 기록의 표현은 명확했다.

“분자가 0이 아니라 필드가 존재하지 않는다.”

후보가 우연히 없었던 것이 아니다. 어떤 카드도 규칙을 통과할 수 없는 계약이었다. 이 검사는 모델을 호출하기 전에 일반 코드로 끝냈어야 한다. 하지만 시스템은 매번 긴 컨텍스트를 구성해 에이전트에게 같은 판정을 다시 맡겼다.

왜 오류 뒤에도 멈추지 않았나

세 종류의 신호가 관찰됐다.

  • 실제 작업 중에도 활동 상태가 initializing으로 남아 600초 후 시간 초과로 처리됐다.
  • Too many open files 오류가 반복됐다.
  • 사용량 창이 100%에 도달한 뒤에도 다음 예약 회차가 유지됐다.

이 오류들은 원인이 서로 다르다. 공통점은 어느 것도 예약 작업을 멈추는 회로 차단기에 연결되지 않았다는 것이다. 정상 종료든 실패든 다음 10분 실행이 남았다. 시간 초과는 복구가 아니라 또 하나의 재시도 트리거가 됐다.

예약 정책 실패 뒤에도 다음 실행 유지 연속 실패 시 자동 중단

정말 아무 결과도 없었나

그렇지는 않다. “결과가 전혀 없었다”고 쓰면 또 다른 과장이다. 일부 회차는 격리 복제본에서 쓸 만한 로컬 패치와 테스트를 남겼다.

익명화한 작업 로컬 산출물 한계
백엔드 라우터 2파일 +55/-4, 로컬 회귀 테스트 미커밋, 실제 메시징 검증 없음
CLI 핸들러 A 5파일 +200/-11, 단위·race·vet·build 실제 CLI·채널 종단 간(E2E) 검증 없음
CLI 핸들러 B 5파일 +278/-9, 로컬 테스트 실제 서비스 종단 간(E2E) 검증 없음
관측 UI와 조립 코드 7파일, Go·Node 테스트 브라우저·원격 환경 검증 없음
서비스 회귀 테스트 2파일 +81/-1 패치 의존성 문제로 테스트 미완주
자동화 요청 JSON 재사용 가능한 패치 2개 현행 소스에 적용하지 않음

실제 작업일지에는 “로컬 패치 완료, 카드 종료 판정은 보류”, “집중 테스트는 실행 완료가 아니다”라는 문장이 남아 있다. 이 구분은 옳다. 로컬 변경은 전달 완료가 아니다.

외부 반영을 승인 없이 금지한 것은 안전했다. 문제는 검토 가능한 패치와 검증 근거를 사람에게 넘기는 인수인계 종료 경로가 연결돼 있지 않았다는 것이다. 작업 품질과 자동화 효율은 별개의 축이다. 일부 패치가 유효해도, 10분마다 같은 준비 절차를 다시 밟는 시스템이 효율적인 것은 아니다.

영향

첫 사용량 창은 관찰 구간에서 16%에서 100%로 상승했다. 다음 사용량 창도 2%에서 93%까지 상승했다. 사용량이 고갈된 뒤에는 의미 있는 최종 응답 없이 끝난 세션도 이어졌다.

세션 84개와 작업일지 72개는 완료된 업무 수가 아니다. 자동화 시스템에서는 활동량과 성과를 분리해 측정해야 한다.

  • 실행 횟수는 많았는가?
  • 유효한 변경을 만들었는가?
  • 검증을 통과했는가?
  • 사람이 검토할 수 있게 전달됐는가?
  • 실제 반영됐는가?

이번 사건에서는 실행 횟수가 압도적으로 증가했지만, 조사 범위에서 확인된 commit·push·PR·배포는 0건이었다. 자동 경보는 없었고, 사용자가 비정상적인 사용량 고갈을 발견하면서 사고가 드러났다.

중단과 복구

발견 직후 다음 순서로 중단했다.

  1. 예약 작업을 일시 정지했다.
  2. 실행 중인 에이전트 프로세스를 종료했다.
  3. 예약 작업 정의를 삭제했다.
  4. 부팅 자동 시작 등록을 해제했다.
  5. 작업 ID, 프로세스, 자동 시작 등록이 모두 사라졌는지 확인했다.
  6. 감사용 실행 기록과 로컬 패치는 보존했다.

자동 시작 설정은 복구 가능한 휴지통으로 이동했다. 다른 예약 작업과 게이트웨이 데이터까지 넓게 삭제하지는 않았다. 원인 경로만 좁게 제거하고, 사후 분석 증거는 남겼다.

재발 방지: 프롬프트가 아니라 시스템이 멈춰야 한다

“다음에는 조심하라”는 프롬프트만으로는 부족하다. 모델이 호출되기 전에, 그리고 모델이 실패한 뒤에 실행 시스템이 강제로 판단해야 한다.

후보가 없거나 예산·시스템 한계를 만나면 중단하고 사람에게 알린다. 작업에 성공했을 때만 검토 가능한 증거 묶음으로 전달한다. 그림을 누르면 원본 크기로 확대된다.

조치의 구현 상태를 구분하면 다음과 같다. 사고 직후에는 원인 경로를 끊었고, 나머지는 운영 시스템에 구현한 뒤 별도로 검증해야 할 제안이다.

조치 상태 동작
예약 작업 정지·삭제, 자동 시작 해제 완료·확인 작업 ID·프로세스·자동 시작 등록의 부재 확인
모델 호출 전 스키마·후보 수 검사 제안 후보 0건이면 모델을 호출하지 않고 알림

생성자·변경자·예산·종료 이유 감사 로그 제안 다음 사고에서 행위자와 종료 원인 추적

완료 상태도 세분화해야 한다.

분석 완료 → 로컬 패치 → 검증 완료 → 리뷰 가능 → 브랜치·PR 전달 → 반영·배포

“에이전트가 일했다”와 “팀이 결과를 인수했다” 사이에는 여러 단계가 있다. 이 상태들을 하나의 completed로 합치면 활동량이 성과처럼 보인다.

아직 모르는 것

사건 보고서에는 모르는 것도 남겨야 한다.

  • 최초 예약 작업을 만든 사람이나 명령은 기록이 없어 특정하지 못했다.
  • 기록된 토큰과 실제 청구량의 관계는 확인하지 못했다.
  • 하위 에이전트 사용량은 총계에 포함되지 않았을 수 있다.
  • 중간 감사에서 “작업함”으로 분류된 모든 회차를 전수 검증하지 않았다.
  • 자기 작업일지 재입력이 전체 토큰의 몇 퍼센트를 차지했는지는 계산하지 않았다.
  • 발견된 로컬 패치가 최신 원격 코드에도 그대로 유효한지는 확인하지 않았다.

따라서 “모든 회차가 공회전했다”, “4.38억 토큰이 그대로 과금됐다”, “Codex 자체 버그였다”라고 주장하지 않는다. 확정할 수 있는 것은 중단 조건이 없는 로컬 자동화 루프가 대규모 사용량과 반복 실행을 만들었다는 사실이다.

마지막 메시지

에이전트 자동화의 위험은 한 번의 잘못된 답변에만 있지 않다. 일을 할 수 없는 상태에서도 계속 실행되는 시스템, 실패를 비용으로 바꾸는 재시도 정책, 자기 산출물을 다시 먹는 입력 구조가 더 큰 사고를 만든다.

에이전트에게 권한을 주기 전에 먼저 중단 조건, 예산, 완료의 정의를 줘야 한다. 그리고 그것은 프롬프트의 부탁이 아니라 실행 시스템의 강제 규칙이어야 한다.

조사 방법과 출처

자체 사건 수치는 예약 작업 정의, 프로세스 계층, 로컬 세션 메타데이터, 사용량 기록, 작업일지와 오류 로그를 교차 확인해 집계했다. 보안상 원본 감사 자료는 공개하지 않고 익명화한 집계표와 자체 제작 도표를 시각 증거로 제공했다.
